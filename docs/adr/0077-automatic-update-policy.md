# ADR 0077 — Background update policy preserves explicit installation authority

Status: implemented. Fresh non-author source/focused review found and rechecked cancellation and painted-action repairs; original failures remain recorded. The final main combination passed its complete 800-input engineering gate and matching macOS package preparation. Limited native wide-window policy save/reopen and SSH/draft preservation are observed; minimum native geometry, downloaded release installation/rollback, publisher signing and other desktop platforms remain open in the [main combination record](../testing/records/2026-10-08-update-toolbar-main-combination.md). The [candidate record](../testing/records/2026-10-08-automatic-update-policy.md) preserves earlier source epochs separately.

## Context

Release discovery, verified staging and an explicitly started rollback helper already exist. Recreating the About panel for each opening made its visibility the lifetime of a manual request, and there was no persisted background cadence or optional automatic download. The user's update requirement needs a long-lived service and clear saved policy, without turning a downloaded package or model output into installation authority.

## Decision

The workspace creates one update service. Showing or hiding the modal only changes visibility and focus; a weak foreground poll remains owned by the service. Core metadata contains typed Disabled/Daily/Weekly policy, optional automatic download and last completed check time. Missing legacy policy defaults to Daily with download off. Present malformed policy is rejected; application load failure pauses background work until a successful save or reload, rather than sending network requests under fallback defaults. All saves use the existing off-thread optimistic StateStore transaction; check metadata merges into a concurrent user save or gets its own bounded-retry save. History and policy persistence do not invalidate command suggestion identities.

Monotonic deadlines enforce a 60-second startup delay, normal daily/weekly interval, and exponential 15-minute to 6-hour failure backoff. Persisted wall time only seeds a new deadline; backward clock changes wait at most one normal interval and an overdue check still observes startup delay. A single owned Tokio task and foreground receiver belong to an immutable request identity. Manual checks supersede automatic work; active manual work excludes a scheduled request. Policy changes revoke the old generation. The result must match nonce, fixed repository source, current application version, captured platform and policy generation; a staged package also matches the complete discovered release.

A ready package is retained independently while checking for new metadata or staging a replacement. Errors, unchanged releases and cancellation of an active request restore it; only a verified replacement consumes the old package. With no active request, the Ready button explicitly offers to discard the downloaded update. Automatic background discovery may download, never install. Saving policy or a manual check does not implicitly download. The explicit install action alone invokes the existing helper. Stage guards dispatch filesystem cleanup off the foreground thread, including stale callback or abandoned blocking outcomes; active blocking work may complete after cancellation and has no installation authority.

The service reads settings after every successful workspace save and local profile-state reload. Clean drafts follow reloaded policy; dirty drafts retain their selected policy and receive only authoritative check metadata. There is no custom update URL, prerelease channel, telemetry, customer context, new dependency or silent installation. Test-only endpoint fields are absent from production; owned loopback fixtures exercise the same parser, checksum, extraction, task and completion paths.

## Verification and limits

The 26 new tests cover strict policy and legacy loading, actual optimistic disk conflicts, startup/clock/backoff boundaries, held HTTP requests, manual preemption, actual future cancellation, late blocking-stage cleanup, real archive download/verification, periodic checks and cancellation from Ready, failed replacement retention, hidden-service history persistence, and bilingual Light/Dark controls in minimum controlled windows. The final service/workspace test runs passed; the same held-request case failed under the preserved old cancellation source and passed after repair. Run identities and the older full-gate boundary are recorded separately. A native desktop is required for native UI/keyboard acceptance.

Existing unsigned packages and unverified installed-directory permissions remain a release limitation. SHA-256 integrity is not publisher authentication, and this policy does not close signing/notarization or platform installation acceptance. Controlled tests hold a runtime owner and explicitly release blocking work; they do not prove a bounded whole-native-application quit during long extraction. That lifecycle acceptance remains open. Application shutdown and operating-system interruption can leave a private temporary stage; no update is resumed or installed from it automatically.

## Painted action identity

Background work can replace the service state before its previously painted button receives a pointer event. Download captures the displayed complete ReleaseInfo. Return, reveal, install and discard capture the exact stage identity (complete release, digest, archive and payload); stage review is shared per render. CancelIntent separates RequestIdentity from downloaded-stage identity. Activation revalidates the same live owner and requires no active request for stage actions. Stale controls never switch intent or authorize a replacement. Six preserved-listener raw pointer controls failed with the old handlers and passed with the guards; three additional identity and fresh-action cases passed. Installation controls set the platform target to None before entering install, ensuring no helper or installation-root access on any OS. Final full/native verification is tracked in the main combination record.
