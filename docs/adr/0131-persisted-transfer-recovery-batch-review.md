# ADR 0131: 持久化传输恢复的有序批量整理

- 日期：2026-11-15
- 状态：接受；实现与验收结果见本批测试记录。
- 范围：FilesPanel 的恢复记录选择、逐条审核队列与显式批量丢弃。

## 背景

持久化恢复日志已经支持单条记录的检查、重新审核、显式续传和丢弃。
多条记录需要更方便的整理入口，但列表选择不能成为连接、主机确认、
只读检查或传输执行的授权。每条记录的 OS 文件锁 claim、当前 SSH
会话绑定与既有审核流程仍然是独立的边界。

## 决策

恢复列表使用有界的复选框选择，展示已选数量。建立审核队列时按当前
列表顺序保存记录 ID，不按点击先后或 UUID 排序。队列仅保存在面板内存，
绑定当前 session token，并有可撤销的 revision；队列本身不持有全体
记录的 claim，也不生成批量传输许可。

“逐条进入审核”只处理当前队首。后台取得该记录的独占 claim，再核对
持久化记录与选择时的快照，之后进入既有的
`Inspect → Review → Confirm`。当前保存连接必须匹配；无连接绑定的记录
必须先明确确认当前 SSH 主机。完成或放弃一条审核后，下一条仍需用户
再次进入，不能自动检查、连接或执行。

取消审核、关闭详情、导航、会话退休、记录消失和迟到回调撤销待审核状态。
已经显式确认并交给传输 worker 的任务继续由原任务持有 claim，按真实
终态更新日志；队列撤销不能重放这些任务，也不能释放 worker 正在使用的
所有权。

批量丢弃首先显示完整选中集合和本地元数据删除说明，再使用现有确认区
进行明确确认。后台逐条执行 `claim → 核对记录快照 → remove_with_claim`，
每条 claim 处理结束即释放。Busy、记录变化或读写失败独立报告，未处理
记录保留；未知或部分完成的结果从存储重新加载，不自动重试删除。
该操作不修改传输文件。

UI 继续使用主题 registry、Palette 和语义 token，支持霜白、曜石、雾紫，
不在恢复业务代码内判断主题 ID。中英文、可访问性名称、换行操作条与
滚动详情共用同一结构，确认区复用现有固定布局。

## 工程与验证

选择和审核状态留在 app 层；core 继续负责日志、原子发布和 claim，
session 负责只读计划与传输。阻塞存储操作继续在后台执行，无新增依赖。

本批统一执行完整工程门禁、官方依赖检查、真实 Podman/OpenSSH 互操作和
新的非作者严格只读复核。开发期间只执行编译与恢复行为专项。具体计数、
源码归属、失败记录及未验证边界见
[集中验证记录](../testing/records/2026-11-15-transfer-recovery-batch-integration.md)。
GPUI 测试、受控 SSH 或 macOS 单机通过不能代签 Windows/Linux 原生、
完整辅助技术、真实客户服务和发行安装验收。
