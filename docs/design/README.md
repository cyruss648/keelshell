## 参考选型

| 来源 | 适合借鉴的内容 | 在KeelShell中的用途 |
| --- | --- | --- |
| [Zed主题文档](https://zed.dev/docs/themes)及公开原生实现 | system/light/dark配置、两套主题、桌面开发工具的高密度工作区 | 作为GPUI原生产品的工程参考，研究状态与外观切换；不引入其终端产品范围 |
| [Fluent 2颜色体系](https://fluent2.microsoft.design/color) | 中性色/品牌色/语义色分工、明暗状态与token、克制使用强调色 | 建立跨平台语义token与清晰状态层级，不混用多个完整视觉体系 |
| [DBX AI助手](https://dbxio.com/cn/docs/ai-assistant) | 命名配置、API与本地CLI、上下文、Ask/Agent与执行确认 | AI配置、侧栏、步骤和审核的交互参考；授权由SSH领域强制 |
| [WCAG文本对比说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) | 普通文字4.5:1、大字3:1的可读性指标 | 作为界面token的设计检查门槛；满足颜色检查不等于全部原生辅助技术验收 |

选型判断：以原生工具型工作区为基础，以一个统一的语义色/组件体系提升品质。专业感来自信息层级、精确状态、稳定对齐与明确操作，并不取决于更多渐变、卡片或装饰色。终端、文件与AI应属于同一产品，避免各面板自成一套样式。

## 要持续维护的设计内容

- Token：画布/表面/边界/文本/强调/状态/焦点，以及字阶、间距、圆角和密度；浅色和深色分别定义。
- 组件：工具栏、连接行/卡片、目录树、标签、徽章、进度、表单、对话框、审核条、空/加载/错误/未知状态。
- 场景：空启动、单/双SSH、AI打开、长连接名、大目录、在途传输、审核、重连与取消；中文/英文和窄/宽窗口。
- 证据：每张原生截图关联精确构建摘要和隔离数据，单独记录未验收平台与失败，不用概念图替代实际验收。

## 可用技能与方法

当前开发环境已有Product Design的`audit`、`ideate`、`image-to-code`，以及`imagegen`和`diagram-design`。审查适合真实截图/流程与可访问性检查；视觉探索适合在既有界面上比较主题、密度和层级；图像生成适合概念稿与位图资产；架构图适合解释本地智能体/MCP/审核的数据流。`image-to-code`主要针对前端原型，原生GPUI实现仍须按实际组件API、事件与平台运行验证，不能将网页原型当成可交付桌面应用。

后续可在仓库维护项目专用设计约定，供所有实施代理使用；用户未要求安装新的技能或修改个人记忆，因此本轮仅登记可用工具与项目资料。不依赖付费Figma库或额外插件才能开发。
