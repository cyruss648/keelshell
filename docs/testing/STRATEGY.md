# 验证策略

- 单元：连接校验、状态转换、路径/命令构造、脱敏、上下文预算、版本迁移。
- 集成：隔离目录的持久化往返与损坏恢复；远程终端输入输出/resize/退出；loopback SSH 主机信任、认证、SFTP 和隧道；loopback AI HTTP 成功/失败/超时/恶意响应。
- UI：真实 GPUI 窗口启动、输入焦点、快捷键、中文输入、终端颜色和调整窗口、连接编辑、文件与 AI 流程。
- 平台：macOS arm64 本机验收；Windows x64/arm64、Linux x64/arm64 分别原生验证。CI 文件存在不代表任务已运行。
- 门禁：格式、Clippy、单元与集成、依赖版本策略；功能提交应包含测试记录。

外部服务和真实凭据未提供时，使用隔离 loopback fixture；不凭 mock 结果声称生产互通。所有测试有明确超时，避免挂住工作。

## 阶段集中验证

2026-11-15 起按用户要求减少重复的全仓构建与评审。将可以独立开发、接口已明确的
功能组合成一个交付批次；测试代码与功能一起编写，完整测试执行集中在集成之后。
不会把整个产品的所有平台和功能都写完才首次验证。

1. 开发时只运行受影响包的编译检查及必要的行为回归。连接身份、凭据、远端写入、
   持久化和异步失效等边界发生变化时，立即运行对应专项，避免后续实现建立在错误
   接口或状态模型之上。子 agent 不重复执行整仓 `scripts/check.py`。
2. 子任务完成后先集成到同一工作树，核对各功能新增的具体测试名，再统一执行
   `scripts/check.py`、依赖新鲜度检查和本批相关的真实联调。已有门禁绑定原输入，
   不能替代集成后源码的验证。
3. 集中处理失败。每次修复先重跑失败用例和受影响专项；只有新的源码、依赖或
   未解决风险需要时才扩大检查范围。最终冻结源码必须有一次完整成功门禁。
   文档文字更新不触发无关 Rust 全仓重跑。
4. 新的非作者 agent 对冻结输入完成代码与功能复核，使用独立 target 或明确披露的
   预构建产物，只重跑有意义的风险专项；不为了重复计数再跑作者已完成的全部门禁。
   发现阻塞问题时立即在本批证据目录写入 `review-*/notice-*.md`，给出位置、
   触发和证据边界；父线程每次观察长门禁进度时同时检查新 notice，不只等待
   最终报告或跨会话消息。来源与终态未确认的投递不能当成已通知。需要修改
   源码时，先真正停止并回收旧门禁，保留原件，再验证新冻结候选。
   发现项修复后核对最终源码差分及必要回归。
5. 完成本批门禁和复核后形成正式本地功能提交，集中更新 HANDOFF、ROADMAP 和测试
   记录，再清理自有临时资源。开发中间状态不得写成已验证或产品验收通过。

从 2026-11-16 本批收口之后的批次起，将非作者源码复核、失败修复和对应专项
放在最终完整门禁之前：候选代码集成后即可交非作者，源码批准可保留完整门禁待定
条件，由父在相同最终输入上绑定成功回执。所有已知发现关闭、窄差分复核完成后，
才启动最终 `scripts/check.py`。全门禁期间并行处理文档、证据封存准备和资源读回，
避免审查仍在发现源码问题时过早启动长门禁，随后又必须中止重跑。
这不取消开发期的关键行为回归，也不把旧输入的成功移签到新输入；
真实桌面与协议专项仍按实际影响集中执行，保持各自验收范围。

固定远端脚本、协议帧或平台分派发生变化时，在最终长门禁前集中运行受影响的
transport 包测试，使用 `cargo test -p keelshell-session --locked --no-fail-fast`
一次收集各 integration target 的问题。既有测试可能把完整旧命令当作正文，
或把新采集器对子进程的清理误认为目标进程操作；应明确新包装与原正文的边界，
保留精确正文、超时、只读、数值和生命周期断言，不能直接删除旧安全检查。
只有实际失败或未解决风险需要时扩大该专项，不让子 agent 重复整包或全仓运行。

持久证据需在删除临时目录前核验原文字节、压缩文件和解压摘要；正式提交前还需
核对每项原件实际存在于 Git index/blob，不能只验证磁盘副本。仓库全局忽略
`*.log`，证据目录若保存原始日志，应使用局部 `.gitignore` 例外显式纳入。
原件的 CRLF、空白和末尾空行使用局部 `.gitattributes` 保留，不裁剪报告或日志
来通过 diff check；失败检查与修正另记回执。提交后将同一工程冻结和原件清单
再与精确源码提交及当前文件逐项绑定。纯文档、提交绑定和证据属性修正不触发
输入未变的完整 Rust 门禁重跑。

Quality 的 push 触发自 2026-11-16 起忽略只涉及 `docs/**` 的提交，
避免证据回执推送取消同分支正在执行的源码检查。PR 触发保持原样。
任何非 docs 路径改动仍运行三平台完整工作流。归档/清理的纯文档提交必须
继续用工程完整集合和 Git blob 绑定最近实际验证的源码提交；
不把未启动的文档 SHA 工作流写为精确 SHA CI 通过，也不借此省略源码门禁。

原生 macOS/Windows/Linux、IME、辅助技术和发行安装仍按各自证据验收，可以在批次
验收时集中执行；不能用本机编译、受控协议或 headless GPUI 通过替代。
