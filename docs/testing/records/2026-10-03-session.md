## Native PTY behavior

The fixture launches actual native child processes through `portable-pty`. Tests cover TTY detection, raw output bytes and exit status, working directory/environment, interactive input, terminal dimensions, invalid dimensions, oversized writes, and closing while the bounded output queue is full.

Close explicitly terminates both the shell process group and a distinct foreground job group obtained from the PTY. The foreground-job test runs interactive Bash with `sleep`, verifies the job PID has exited, and requires the reader to complete before close reports success. This ownership model does **not** claim control over descendants that deliberately detach into another session with `setsid`; Windows native process-tree behavior remains unverified.

## SSH, SFTP and forwarding

Tests use a real `russh` server and actual encrypted SSH/SFTP packets. The fixture filesystem is in memory, not an operating-system SFTP server.

- Unknown host keys stop before authentication. A changed pinned key is rejected despite valid credentials.
- Password rejection, ephemeral private-key signature authentication, separate stdout/stderr, exit status, output-size limits, interactive UTF-8 shell input and PTY resize are exercised.
- SFTP covers list, read limits, mkdir, rename, remove, upload and download. Download refuses to overwrite an existing local file.
- Directory entry limits, server readdir failure and timeout close the dedicated subsystem and release fixture directory handles.
- Local and remote TCP forwarding transport real bytes. Explicit close removes the listener and owned streams. If remote port allocation times out before its acknowledgement, the connection is disconnected to release a possibly allocated listener whose port is unknown.
- SSH agent authentication remains implemented but untested against a real user agent. Agent, external OpenSSH servers, device-specific authentication and production network failures are not established by these fixtures.

## Atomic remote file replacement

`write_atomic` and `upload_atomic` require the server to advertise `posix-rename@openssh.com` **version 1**. Unsupported servers are rejected before staging or modifying the destination. Files are streamed in 32 KiB blocks into a unique, exclusively created file in the same directory, closed completely, then published with the negotiated POSIX rename extension. Existing rwx mode bits are copied; new files use mode 0600. Symlinks and non-regular destinations are refused. Ownership, ACLs and special mode bits are not preserved.

The four atomic integration cases establish:

1. Replacement and streamed upload publish complete content and leave no temporary entry on success.
2. Missing extension support creates no temporary entry; a server write failure after an accepted prefix preserves the original bytes and the cleanup barrier removes staging.
3. Cancellation after a real temporary-file prefix preserves the original bytes, and explicit `SftpSession::close()` waits for cleanup.
4. SSH disconnect during a subsequent write leaves the original intact when a new SSH connection reads it.

Temporary cleanup is best effort after loss of transport; a uniquely named staging file can remain remotely. Cleanup tasks are bounded to two seconds and explicit SFTP close allows up to two more seconds for protocol shutdown. If the final rename succeeds but its acknowledgement is lost, the destination can contain the complete new content even though the client reports an error. The guarantee is atomic visibility of either the complete old or complete new file, **not** crash durability or a promise that an uncertain write did not occur. The lower-level `write`/`upload` APIs still truncate directly and are documented accordingly; interactive file operations use the atomic APIs.

Protocol reference: [OpenSSH PROTOCOL, SFTP extension negotiation and POSIX rename](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL).

## Controlled GUI acceptance service

Run `cargo run -p keelshell-session --example loopback_fixture -- 600` from the workspace, or use `target/debug/examples/loopback_fixture 600` after building it. The optional argument is its lifetime in seconds (default 60, range 1–3600); Ctrl-C also stops it. It binds exclusively to `127.0.0.1` on a random port and prints only `port`, the fresh `fingerprint`, and its temporary filesystem `root`.

Connect with username `fixture` and password `keelshell-ui-test`. These are public fixture credentials, not a real account. Verify the printed fingerprint in the application's host-key approval flow. Every process run generates a different host key. The shell only echoes UTF-8 bytes with a colored banner and prompt; it rejects all exec requests and does not invoke a system shell. Ctrl-D closes that shell. `/welcome.txt` contains a small English/Chinese document and `/uploads` is an empty directory. SFTP operates on real temporary files, supports atomic replacement on Unix, rejects parent traversal and existing symlink paths, and limits individual files to 16 MiB. The service is test infrastructure, not a hardened multi-user SFTP daemon. It does not provide a resource-monitor or forwarding fixture.

`cargo build -p keelshell-session --example loopback_fixture` and `cargo clippy -p keelshell-session --all-targets -- -D warnings` passed. `cargo test -p keelshell-session --example loopback_fixture` passed three tests: parent traversal refusal, symlink escape refusal, and actual filesystem exclusive staging/replace-after-close. A one-second executable smoke run verified the three stdout fields, normal timer exit, and temporary-root deletion. These checks prepare the service for GUI acceptance; they do not themselves establish that the GUI completed an SSH or file-edit workflow.

## Remaining proof boundaries

The SSH bridge has bounded queues, explicit cancellation, a registered cleanup barrier, coalesced resize requests and no input replay on an uncertain write. The 8 MiB simultaneous echo case passed and verified every byte while input and output exceeded SSH window capacity. Its first run timed out because the fixture echoed from `Handler::data` without consuming its own bounded channel queue; the fixture now runs an actual channel reader/writer. This failure was in the fixture, and its successful replacement establishes full-duplex transport behavior. Native GUI key events, IME composition, GPU painting and application shutdown are separate application-level checks. Windows and Linux native execution remain unverified.
