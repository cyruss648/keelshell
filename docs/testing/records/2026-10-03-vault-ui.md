# SSH credential vault UI — 2026-10-03

The SSH authentication dialog now uses the encrypted vault through explicit,
bilingual save and unlock actions. Password and private-key-passphrase logins
can use a one-time secret, save a credential or unlock a saved credential. SSH
agent authentication continues without a vault prompt.

## User flow and boundaries

- **Save in vault** asks for the SSH secret, master password and confirmation.
  Saving creates the vault if absent or unlocks the existing vault. A completed
  save returns to a locked prompt and never starts an SSH connection.
- **Unlock and connect** asks for the master password each time, resolves the
  bound credential and uses the existing pinned-host SSH connection path. No
  unlocked vault or master password is cached in the workspace.
- **Use one-time secret** clears the current inputs and bypasses persistence.
  **Unlink credential** persistently removes the profile reference without
  needing the master password. Its encrypted entry remains on disk, as stated
  in the dialog; this is not deletion or secure erasure of the vault entry.
- The vault lives beside the configured `StateStore` file, so isolated fixture
  configurations use an isolated `vault.json` as well. KDF, vault reads/writes
  and state persistence run on background workers, outside the GPUI event loop.
- The encrypted payload contains host, port, username, authentication method and
  private-key path. Every unlock compares these values against the captured
  connection before admitting a network connection. A hand-edited state file
  cannot reuse a saved reference for another destination. Renaming a profile or
  changing its group retains the reference; editing its target/auth removes it.
- Each save creates a fresh entry before saving the reference in `state.json`.
  Those files are not one transaction: a failed/cancelled second stage can leave
  an unreferenced encrypted entry. Previously saved entries are not overwritten.
  A state conflict requires saving other work and restarting the app to reload
  configuration before retrying; reopening the dialog does not refresh its
  snapshot. Credential-save failure messages state that password inputs were
  cleared, while ordinary settings-save failures continue preserving drafts.
- Closing a busy dialog invalidates its foreground completion and never starts
  a connection. A write already admitted can still complete after closure; if
  the state-save stage already began, the saved reference may also persist.
  Both the busy Close action and its explanatory text state this boundary.
- Secret fields are cleared after submission, mode switches and dismissal.
  Owned secret buffers and derived vault keys use zeroizing wrappers, but this
  does not claim guaranteed erasure of GPUI input/undo buffers, allocator copies,
  transient serializer/parser allocations, OS swap or crash dumps.

## Verification

```sh
cargo test -p keelshell-app workspace:: --locked --no-fail-fast
cargo clippy -p keelshell-app --all-targets --locked -- -D warnings
cargo test -p keelshell-app --locked
```

The focused workspace suite passed **14 tests**; the complete app suite passed
**73 tests** with no failures or ignored tests. Clippy passed with warnings
denied. The seven new tests cover:

1. Save through the production buttons, remain locked, preserve bilingual state,
   persist only a reference and unlink without starting SSH.
2. Wrong master password is retryable; dismissing a submitted unlock never
   admits a connection or keeps typed master-password input.
3. External state conflict preserves the external edit, leaves an encrypted
   orphan and does not attach a reference or initiate SSH. Chinese and English
   recovery messages direct the user to restart/reload and accurately report
   the cleared credential inputs rather than claiming they were preserved.
4. Renaming a profile preserves its reference; a changed host removes it.
5. Real masked-input pointer/focus actions do not send typed credentials to an
   underlying terminal; cancel restores focus and clears fields.
6. A saved password is unlocked through the production button and accepted by
   a real TCP loopback russh server. The fixture checks the exact remote user
   and SSH password, proving the master password is not passed to SSH auth.
7. Encrypted payload decoding refuses changed host, port, username,
   authentication method or private-key path while permitting label changes.

The SSH fixture has a deterministic test-only host key, an explicitly supplied
host pin and a bounded lifetime. It validates password authentication only;
native keychain, production SSH interoperability, real private-key login and
Windows/Linux desktop interactions are not established by these tests. The
existing transport tests continue to own unknown/changed host-key rejection.
