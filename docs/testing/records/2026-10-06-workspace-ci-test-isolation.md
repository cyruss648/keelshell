## 已证明的问题与修复范围

新的非作者在精确原提交的独立重建中实际调用生产 `local_claim` 和预留账本。
一个已有本地文件的写入会保守地持有整个本地文件系统，以防硬链接别名绕过。
即使另一个用例使用不同临时目录和远端身份，目录同步的两个方向仍会返回 Busy。
反例只有一个 active、零个 unknown、cost 为一；最后一个所有者释放后恢复准入。
这证明了原场景的进程内测试隔离问题。原 Linux CI 没有调用点或预留快照，
无法确定其具体竞争用例或哪一次准入失败，也不能回溯排除原运行的预算压力。

完整目录同步场景迁入现有的独立本地文件系统测试 binary，与原有五个业务场景
共用 `SCENARIOS` guard。除新 guard 外，原场景正文及三个 helper 逐字相同：
5 秒观察、7 秒终态、3 秒即时拒绝边界不变；40 次子文件发布、并发子写拒绝、
队列等待和真实 TCP/SFTP 收尾断言都保留。没有新增忽略或降低整仓测试并发。
生产预留、未知结果隔离和传输逻辑没有变化。

Windows 两项失败的实际阶段尚无法从原日志定位。其共同收尾中的关闭端口探针
只有 250 ms，且业务时间线原在收尾之后打印。候选为每个测试超时包装增加阶段
说明，将完整业务时间线移至收尾前，并仅把收尾探针外层改为有界 3 秒。
超时仍失败，必须实际得到连接错误；连接成功仍触发失败断言。
生产 1 秒空闲期限和全部业务时间区间断言不变。这是诊断与收尾观察改进，
不能据此断言原 Windows 业务已经通过，需以新提交的实际 CI 验证。
