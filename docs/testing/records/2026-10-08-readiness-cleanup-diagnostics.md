## 问题与改动

主线 `219093c` 的 Windows CI 在后代端口的三秒准备期限失败，原日志没有 Ask 返回及清理终态，因此根因仍为 UNKNOWN。原失败保留，不能由本机成功反推它的原因。

测试准备失败现在先取消原 Ask，再借用其 JoinHandle 等待实际结果。失败收尾使用一个五秒绝对期限：四秒协作等待，必要时 abort 并用剩余一秒等待同一 handle。之后仍触发原准备失败断言，不延长原三秒准备期限、十毫秒轮询、配置的两秒 Ask 或正常路径的五秒 Await。

诊断仅输出固定错误类别、实际 Join 状态和有界目录项计数，不输出文件名、路径、问题、成功正文或错误／panic payload。写入失败不改变取消和等待流程。`scripts/check.py` 显式执行新的 `--readiness-error-tests` 入口；harness=false 的默认执行不替代这十项控制。

## 未验证边界

- Windows 的历史三秒失败原因仍未确定，新的精确提交 Windows 执行尚未完成。
- 十项控制使用自有 yielding Rust future；没有验证 nonyielding 阻塞任务、actual_join=false／terminal=unknown 或真实供应商账户／模型。
- 启动失败、外层控制超时、异常 Drop 和 panic hook 恢复失败未实际注入。异常 Drop 的 abort 请求不等于实际 Join。
- 诊断仅注入首个 prefix 写入失败，后续部分写入／JSON／换行失败没有行为证据。
- 同步文件系统调用和 stderr 锁／写入不能由异步期限硬取消，不宣称 OS 级绝对退出上限。
- 本次不增加 GUI、安装更新、跨平台桌面或完整产品验收。
