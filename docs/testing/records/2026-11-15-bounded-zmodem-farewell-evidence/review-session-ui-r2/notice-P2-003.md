Trigger: the receive has valid ZFIN and retains ordinary peer output (for example a UTF-8 prompt) while waiting for its protocol confirmation or final OO. The actual protocol write/confirmation expires without an already observed shell completion, so `write_and_drain` returns an error and `pump` exits through `?`. A local worker cancellation has the same final cleanup shape. After the exit, `run_with_protocol` calls `protocol.fail()`. In r2, a still-Finishing receiver already returns its retained tail on local cancellation: session `cancel_wire` preserves `Event::Terminal` and controller `transport_failed` returns it; the app `effects` then queues `SessionEvent::Data`. That queue is never delivered to the real `output` sender before the protocol is dropped.

Impact: ordinary terminal bytes successfully received earlier are silently lost on a write-failure/worker-cleanup path. This persists even if CORE-R2-01 correctly preserves the tail through peer-cancellation/Failed core states. Safety result delivery through the shared mailbox does not deliver ordinary bytes held in `protocol.output`. This finding does not reclassify failure, authorize input release, or invalidate per-file save receipts.

Required correction: deliver cleanup-produced terminal output through the existing bounded bridge output path before its owner is dropped, preserving its order and the existing cancellation, UI backpressure and owned-cleanup bounds. Do not turn a failed shell into a successful farewell or clear its input fence before actual transport cleanup. Add a parent-owned regression that drives the production `run_with_protocol` failure/cleanup path with a previously retained ordinary tail and checks the real UI byte receiver, not only controller effects or a direct `pump` call. Cover available output capacity and the chosen bounded behavior under UI backpressure.
